# نصب «کارام» روی هاست اشتراکی cPanel (دامنه‌ی app.hojre24shop.ir)

این راهنما مخصوص **فاز ۱** است: اپ مهمان آفلاین + PWA + ساختار API + دیتابیس.

---

## ۱) پیش‌نیازها

- هاست cPanel با PHP **8.1+** و MySQL/MariaDB
- SSL فعال روی دامنه (Let's Encrypt کافی است) — اپ بدون HTTPS کار نمی‌کند (Service Worker)
- دامنه‌ی `app.hojre24shop.ir` به پوشه‌ای مثل `public_html/app` (یا یک `public_html` اختصاصی) اشاره کند

## ۲) ساخت پوشه‌ها روی هاست

ساختار نهایی این شکلی است:

```
/home/USERNAME/
├── private/                  ← بیرون از public_html (فایل‌های حساس)
│   ├── .env                  ← تنظیمات و کلیدها
│   └── storage/receipts/     ← (فاز ۵) رسیدهای کارت‌به‌کارت
└── public_html/              ← روت دامنه‌ی app.hojre24shop.ir
    ├── index.html            ← از بیلد فرانت (dist)
    ├── assets/               ← از بیلد فرانت
    ├── fonts/  icons/  manifest.webmanifest  sw.js
    ├── .htaccess             ← از deploy/.htaccess
    └── api/                  ← بک‌اند PHP
        ├── .htaccess         ← از backend/.htaccess (بستن دسترسی)
        ├── public/           ← محتوای backend/public (index.php + .htaccess)
        ├── src/              ← کلاس‌های PHP
        └── storage/logs/
```

> اگر `public_html` شما مشترک با سایت اصلی است، بهتر است در cPanel یک **Subdomain** بسازید که DocumentRoot آن یک پوشه‌ی جدا باشد.

## ۳) بیلد فرانت‌اند (روی کامپیوتر خودتان)

```bash
cd frontend
bun install        # یا npm install
bun run build      # یا npm run build

# پنل مدیریت (فاز ۴)
cd ../frontend/admin
bun install
bun run build
```

خروجی اپ در `frontend/dist/` و پنل در `frontend/admin/dist/` ساخته می‌شود.

## ۴) آپلود

1. محتویات `frontend/dist/*` را در `public_html/` آپلود کنید.
2. فایل `deploy/.htaccess` را در `public_html/.htaccess` قرار دهید (جایگزین/ادغام با فایل فعلی).
3. پوشه‌ی `backend/` را آپلود کنید:
   - محتوای `backend/public/` → `public_html/api/`
   - پوشه‌های `src/` و `storage/` → داخل `public_html/api/`
   - فایل `backend/.htaccess` → `public_html/api/.htaccess`
4. پوشه‌ی `private/` را در home اکانت بسازید (بیرون از public_html) و دسترسی `700` بدهید.
5. محتویات `frontend/admin/dist/*` را در `public_html/panel/` آپلود کنید (پوشه را بسازید) — این همان پنل مدیریت است.

## ۵) دیتابیس

1. در cPanel: **MySQL Databases** → دیتابیس و کاربر بسازید و کاربر را به دیتابیس با همه‌ی دسترسی‌ها اضافه کنید.
2. از **phpMyAdmin** دیتابیس را انتخاب و فایل `deploy/install.sql` را Import کنید.
3. جداول ساخته می‌شوند + پلن‌های پیش‌فرض و تنظیمات اولیه درج می‌شوند.

## ۶) فایل .env

1. `backend/.env.example` را به `/home/USERNAME/private/.env` کپی کنید.
2. مقادیر دیتابیس (`DB_NAME`, `DB_USER`, `DB_PASS`) را پر کنید (`DB_DRIVER` روی `mysql` بماند).
3. **`APP_SECRET`** را حتماً یک مقدار تصادفی طولانی بگذارید (خروجی `openssl rand -hex 32`) — راز امضای توکن‌ها و هش کدهای OTP است.
4. `SETUP_TOKEN` را یک مقدار تصادفی طولانی بگذارید (مثلاً خروجی `openssl rand -hex 32`).
5. مطمئن شوید `OPEN_SESSION="0"` است (ورود فقط با کد یک‌بارمصرف — فاز ۳).
6. `OTP_DEBUG` حتماً **«0»** باشد (در حالت ۱ کد در پاسخ API هم برمی‌گردد — فقط برای توسعه‌ی محلی).
7. دسترسی فایل را `600` بدهید.

### ۶-۱) راه‌اندازی ورود با ایمیل (OTP)

- پیش‌فرض `MAIL_TRANSPORT="mail"` است: از تابع `mail()` خود cPanel استفاده می‌شود و نیازی به تنظیم ندارد.
- برای تحویل بهتر، در cPanel یک ایمیل‌اکانت مثل `no-reply@hojre24shop.ir` بسازید و همان را در `SMTP_FROM` بگذارید؛ رکوردهای SPF/DKIM دامنه را هم در DNS تنظیم کنید.
- اگر `mail()` کافی نبود: `MAIL_TRANSPORT="smtp"` و مقادیر `SMTP_HOST/PORT/SECURE/USER/PASS` را از سرویس‌دهنده‌ی ایمیل بگیرید (پورت 587 با `SMTP_SECURE=tls` یا 465 با `ssl`).
- عیب‌یابی: خطاها در `api/storage/logs/php-error.log` و اگر `MAIL_TRANSPORT=log` باشد، ایمیل‌ها به‌جای ارسال در `api/storage/logs/mail.log` می‌روند (فقط برای تست).

### ۶-۲) راه‌اندازی ورود با بله (ربات)

1. در بله به **@BotFather** پیام دهید و یک ربات بسازید؛ توکن و نام کاربری ربات را بردارید.
2. در `.env` بگذارید:

```
BALE_BOT_TOKEN="توکن_ربات"
BALE_BOT_USERNAME="نام_کاربری_ربات_بدون_@"
```

3. از این لحظه دکمه‌ی «ورود با ربات بله» در اپ ظاهر می‌شود؛ کاربر کد ۶ حرفی را برای ربات می‌فرستد و کد ورود به همان چت برمی‌گردد.
- `BALE_API_BASE` را خالی بگذارید (فقط برای تست محلی با سرور ساختگی است).
- کاربران باید یک‌بار به ربات پیام داده باشند (با همان لینک «باز کردن بله» خودکار انجام می‌شود).

## ۷) تست سلامت API

آدرس زیر را باز کنید:

```
https://app.hojre24shop.ir/api/health
```

پاسخ مورد انتظار:

```json
{ "ok": true, "service": "karam-api", "database": "connected", ... }
```

## ۸) ساخت ادمین اصلی (یک‌بارمصرف — پیش‌نیاز پنل مدیریت)

از **cPanel Terminal** (یا SSH):

```bash
cd ~/public_html/api
php install/setup-admin.php "SETUP_TOKEN" "admin" "Ramz-e-Ghavi-123"
```

> توجه: پوشه‌ی `install` روی وب بسته است؛ اجرای CLI امن‌ترین راه است.
> بعد از اجرا، اسکریپت **خودش را به `setup-admin.disabled.php` تغییر نام می‌دهد** و فایل `.installed` می‌سازد؛ دوباره اجرا شدنش غیرممکن است.
> این ادمین همان حسابی است که در پنل مدیریت (`/panel`) وارد می‌شوید.

## ۹) تست اپ

1. `https://app.hojre24shop.ir` را در موبایل/دسکتاپ باز کنید.
2. بار اول اینترنت لازم است؛ بعد از آن اپ کاملاً آفلاین کار می‌کند (Service Worker).
3. در DevTools → Application → Service Workers، وضعیت «activated» را ببینید.
4. اینترنت را قطع کنید و صفحه را رفرش کنید — اپ باید کامل بالا بیاید.
5. یک کار بسازید، تیک بزنید، حذف کنید؛ مرورگر را ببندید و باز کنید — داده‌ها از IndexedDB برمی‌گردند.
6. **تست سینک (فاز ۲):** تنظیمات → «پشتیبان‌گیری در حساب کاربری» → ورود با ایمیل (کد یک‌بارمصرف) → پس از چند ثانیه باید «سینک شد ✓» ببینید. یک کار بسازید؛ با یک دستگاه دیگر (یا همان حساب) وارد شوید — داده‌ها باید یکی باشند.
7. **تست ورود با ایمیل (فاز ۳):** کد ۶ رقمی به ایمیل می‌رود؛ وارد کنید. ارسال مجدد تا ۶۰ ثانیه قفل است؛ ۵ تلاش اشتباه کد را باطل می‌کند.
8. **تست ورود با بله (فاز ۳):** «ورود با ربات بله» → کد ۶ حرفی را برای ربات بفرستید (لینک آماده) → کد ورود در چت بله می‌آید → وارد کنید.
9. **تست نشست‌ها (فاز ۳):** از دو دستگاه/مرورگر وارد شوید؛ در شیت حساب، «نشست‌های فعال» هر دو را نشان می‌دهد؛ نشست دستگاه دیگر را حذف کنید — آن دستگاه در اولین درخواست از حساب خارج می‌شود.
10. **تست خروج و ماندگاری (فاز ۳):** صفحه را ببندید و باز کنید — بدون ورود مجدد وارد حساب می‌شوید (Refresh Token). «خروج از حساب» نشست سمت سرور را هم باطل می‌کند.

## ۱۰) پنل مدیریت (فاز ۴)

### آپلود پنل

1. محتویات `frontend/admin/dist/` را در `public_html/panel/` آپلود کنید (پوشه را خودتان بسازید).
2. آدرس: `https://app.hojre24shop.ir/panel/` — با همان ادمینی که در گام ۸ ساختید وارد شوید.

### امکانات پنل

| بخش | کارهایی که می‌توانید بکنید |
|---|---|
| داشبورد | تعداد کاربران، ثبت‌نام ۷روزه (نمودار شمسی)، کاربران پرو/مسدود، نشست‌های فعال، درآمد ثبت‌شده |
| کاربران | جستجو (ایمیل/نام/UUID)، جزئیات کامل، مسدودسازی/رفع مسدودی (خروج فوری همه‌ی دستگاه‌ها)، اعطای اشتراک پرو (ماهانه/سالانه/دائمی — تمدید از انتهای اشتراک فعلی)، لغو پرو، ابطال نشست‌ها |
| پلن‌ها | ویرایش قیمت/عنوان/توضیح و فعال/غیرفعال — همان قیمتی که صفحه‌ی پرداخت اپ نشان می‌دهد |
| اطلاعیه‌ها | ساخت/ویرایش/حذف با نوع اطلاعیه/هشدار/پرو |
| تنظیمات | حالت تعمیر، درگاه‌ها، کارت‌های بانکی، نسخه‌ی حداقل اپ — فقط کلیدهای مجاز و با اعتبارسنجی سمت سرور |
| رخدادها | کامل‌ترین لاگ اعمال مدیریتی: چه کسی، چه کاری، از چه IP و چه زمانی |

### امنیت پنل

- ۵ تلاش ناموفق ورود → حساب ۱۵ دقیقه قفل می‌شود.
- عمر نشست پیش‌فرض ۱۲ ساعت (`ADMIN_SESSION_TTL_HOURS` در `.env`)؛ «خروج از پنل» نشست سمت سرور را حذف می‌کند.
- همه‌ی عملیات تغییردهنده با CSRF محافظت می‌شوند و در `audit_logs` ثبت می‌گردند.
- اگر تیم پشتیبانی داشتید: رکورد نقش `support` از قبل آماده است (فقط مشاهده‌ی کاربران و سفارش‌ها) — ساخت ادمین دوم فعلاً با SQL/توسعه‌ی بعدی است.

## ۱۱) نکات مهم

- **به‌روزرسانی:** بعد از هر تغییر، دوباره `bun run build` و آپلود `dist`. نسخه‌ی جدید SW خودش کش قبلی را پاک می‌کند؛ اگر آپدیت فوری لازم شد در DevTools → Application → Service Workers → Unregister + پاک کردن Cache.
- **CSP:** سخت‌گیرانه روی `'self'` است. هر منبع خارجی (فونت، اسکریپت CDN و ...) بلاک می‌شود — عمداً.
- **امنیت نصب (گام ۱):** فایل‌های عیب‌یابی `diag*.php` از پروژه حذف شدند — دیگر آپلودشان **لازم نیست**؛ اگر روی هاست از قبل هستند، حذفشان کنید. .htaccess هر درخواست به `diag*.php` و مسیر `install/` را با 403 می‌بندد (حتی اگر فایل جایی آپلود شده باشد).
- **میکروفون:** طبق برنامه، سرویس وویس‌به‌متن فعلاً ساخته نمی‌شود؛ همه‌ی دکمه‌های میک ظاهر غیرفعال دارند.
- خطاهای PHP در `public_html/api/storage/logs/php-error.log` ثبت می‌شوند.

## ۱۲) ارتقا به فاز ۴.۵ (نصب‌های موجود — یک‌بار)

۱. **دیتابیس:** در phpMyAdmin فایل `deploy/upgrade-v0.5.sql` را Import کنید (ستون `users.gender` + کلیدهای تنظیمات جدید — امن برای اجرای تکراری).
۲. **بک‌اند:** محتوای `backend/` را جایگزین کنید (کلاس‌های جدید `Support/Settings.php` و `Services/Sms.php` خودشان لود می‌شوند).
۳. **اپ و پنل:** `frontend/dist` → `public_html` و `frontend/admin/dist` → `public_html/panel` (جایگزین کامل).
۴. `.env` نیاز به تغییر ندارد؛ ولی از این به بعد این موارد را می‌توانید **از خود پنل** تنظیم کنید (اولویتشان از .env بیشتر است):
   - توکن/نام ربات بله، مسیر ایمیل و SMTP، پروایدر پیامک
   - حالت تعمیر، بستن ثبت‌نام، سقف آیتم سینک
   - ویس (خواندن صوتی کارها)، کارت‌های بانکی و راهنمای پرداخت

### ۱۲-۱) شورتکد ورود OTP (پنل → «شورتکد ورود OTP»)

- میان‌برها **از تنظیمات سرور** خوانده می‌شوند (پنل → تنظیمات → گروه «شورتکد ورود مالک») — ایمیل/شماره‌ی واقعی شما دیگر در کد نیست.
- شورتکدها فقط به ادمین واردشده با دسترسی `users.manage` برگردانده می‌شوند؛ ناشناس هیچ اطلاعاتی نمی‌بیند.
- «دریافت کد» → کد از سرور مستقیماً در پنل نمایش داده می‌شود → «درج خودکار» → «تأیید و ورود» → نشست واقعی کاربر صادر می‌شود (برای تست جریان ورود بدون دسترسی به ایمیل/تلگرام/پیامک).
- در کانال تلگرام باید یک‌بار از حساب تلگرام خودتان روی «باز کردن تلگرام» بزنید و START بفرستید؛ پنل خودش poll می‌زند و کد را نشان می‌دهد.
- همه‌ی این اعمال در «رخدادها» با اکشن‌های `otp.shortcut_*` ثبت می‌شوند.

### ۱۲-۲) تم جنسیتی و پشتیبان‌گیری (اپ)

- بعد از اولین ورود، پنجره‌ی «ظاهر کارام را انتخاب کنید» باز می‌شود: دخترانه = تم صورتی، پسرانه = تم فیروزه‌ای. تغییر بعدی از «تنظیمات → ظاهر اپ».
- «تنظیمات → پشتیبان‌گیری از داده‌ها»: دریافت فایل JSON و بازیابی با ادغام امن (هیچ داده‌ای از بین نمی‌رود)؛ با حساب ابری، بعد از بازیابی خودکار سینک می‌شود.

### ۱۲-۳) ورود با شماره موبایل (پیامک)

- پنل → تنظیمات → «پروایدر پیامک»: آدرس API شرکت پیامکی + متد + هدرها (JSON) + قالب بدنه با `{phone}` و `{code}`.
- تا وقتی آدرس تنظیم نشده، کانال در حالت log کار می‌کند (کد فقط در شورتکد ادمین دیده می‌شود) — برای تست کافی است «کانال ورود با موبایل» را روشن کنید.

## ۱۳) کارایی زیر بار همزمان (پک v17 — هزاران کاربر)

کارام آفلاین‌محور است؛ سرور فقط «سینک دسته‌ای + ورود + بنر» را حمل می‌کند. با لایه‌های v17:

- **کش فایلی (داخل `api/storage/cache`):** تنظیمات (TTL ۱۰ دقیقه) و بنر اطلاعیه‌ها (TTL ۶۰ ثانیه) از کش می‌آیند؛ تغییر از پنل همان لحظه کش را باطل می‌کند. این پوشه باید **قابل نوشتن** باشد (اگر نبود، سرویس بدون کش به کوئری برمی‌گردد و نمی‌شکند).
- **gzip + کش immutable:** فایل‌های hash‌دار assets/فونت با کش یک‌ساله سرو می‌شوند؛ باز شدن دوباره‌ی اپ = صفر دانلود فایل استاتیک.
- **تنظیم هاست (در DirectAdmin):**
  - PHP **۸.۱+** و روشن بودن **OPcache** (در Select PHP Version / PHP Settings — معمولاً روشن است؛ اگر خاموش است روشن کنید). OPcache بدون تغییر کد، سرعت PHP را ۲ تا ۳ برابر می‌کند.
  - **HTTP/2** روی دامنه (در SSL/TLS هاست) — باز و بستن اتصال کمتر، خط روان‌تر.
  - اگر LiteSpeed دارید، کش صفحه‌ی پیش‌فرض برای `assets/` خودش فعال است.
- **مرز واقعی مقیاس:** ۲۰۰۰ کاربرِ همزمانِ «در حال استفاده از اپ» یعنی فقط سینک‌های دوره‌ای؛ MySQL با ایندکس‌های موجود و سقف `api_max_sync_items` این بار را حمل می‌کند. برای «۲۰۰۰ کاربر در همان ثانیه‌ی اول نصب» (burp ثبت‌نام/ورود)، سقف‌های موجود ورود و OTP از سرویس محافظت می‌کنند؛ در صورت رشد جدی، ارتقا به VPS یک گام بعدی طبیعی است — بدون تغییر کد.

## ۱۴) دوره آزمایشی (پک v18 — دو کلید، بدون نصب اضافه)

هر ثبت‌نام جدید می‌تواند چند روز «کارام پرو» را رایگان امتحان کند — پاسخ ساده به تردید «اول امتحان کنم بعد بخرم»:

- **روشن‌کردن:** پنل ← تنظیمات ← گروه «دوره آزمایشی (ثبت‌نام جدید)» ← کلید فعال + طول دوره (پیش‌فرض ۷ روز، بین ۱ تا ۳۰).
- **رفتار:** فقط ثبت‌نام‌های جدید پروی خودکار می‌گیرند (`source='trial'`)؛ به اشتراک‌های فعلی و جریان‌های پرداخت دست نمی‌خورد. کاربر در صفحه پرو می‌بیند: «دوره آزمایشی کارام پرو فعال است · N روز باقی‌مانده».
- **مهاجرت خودکار:** بار اول، مقدار `trial` به ENUM ستون `source` جدول `subscriptions` اضافه و دو کلید ساخته می‌شوند (الگوی DepositSchema — بدون phpMyAdmin). فایل اختیاری `deploy/upgrade-v1.0.sql` فقط کلیدها را پیش‌می‌سازد.
- **خاموش‌کردن:** کلید را خاموش کنید — ثبت‌نام‌های بعدی پروی خودکار نمی‌گیرند؛ دوره‌های در جریان تا پایان روزهایشان باقی می‌مانند.

## ۱۵) بکاپ خودکار روزانه (پک v19 — یک کرون، صفر وابستگی)

هر شب کل دیتابیس (همه‌ی جداول) فشرده و در `storage/backups` (بیرون از webroot) نگه‌داری می‌شود — ۷ نسخه‌ی آخر. اگر هاست مرد، بکاپ با تلگرام زنده می‌ماند.

**نصب (۳ قدم، مثل کرون تلگرام):**
1. DirectAdmin ← **Cron Jobs** ← Add New Cron Job
2. زمان: هر روز 03:30 (دقیقه = `30`، ساعت = `3`)
3. دستور:
   `/usr/local/bin/php /home/USERNAME/domains/app.hojre24shop.ir/public_html/api/cron/backup-db.php`
   (مسیر php و یوزرنیم را با راهنمای کرون تلگرام تطبیق بدهید — همان مسیر است)

**راستی‌آزمایی:** در مرورگر باز کنید:
`https://app.hojre24shop.ir/api/cron/backup-db.php?check=karam-backup-check`
همین صفحه وضعیت آخرین اجرا + فهرست نسخه‌ها + دستور کرون آماده‌ی کپی را نشان می‌دهد.

**گزارش روزانه در تلگرام (اختیاری ولی توصیه‌شده):**
- شناسه چت ادمین را پیدا کنید: به ربات `@userinfobot` پیام بدهید — عدد chat_id را می‌دهد.
- پنل ← تنظیمات ← گروه «بکاپ و پشتیبان (v19)» ← همان عدد را در «شناسه چت تلگرام ادمین» ذخیره کنید.
- از این به بعد ربات، فایل بکاپ را مستقیم برایتان می‌فرستد (تا ۴۵MB؛ بزرگ‌تر = فقط پیام گزارش).

**جزئیات فنی:**
- دو روش dump: اگر `mysqldump` روی هاست باشد از آن استفاده می‌شود، وگرنه dump خالص PHP (بدون exec) — همیشه کار می‌کند. خروجی `.sql.gz` با جای‌گذاری اتمیک.
- سقف نگه‌داری: پیش‌فرض ۷ نسخه؛ با `BACKUP_KEEP` در `.env` قابل تغییر (۳ تا ۶۰).
- قفل تک‌اجرایی: دو بکاپ هم‌زمان ممکن نیست؛ خرابی هر شب فقط یک خط در وضعیت ثبت می‌کند و کرون بعدی خودش دوباره تلاش می‌کند.
- امنیت: `storage/.htaccess` دسترسی وب به بکاپ‌ها را می‌بندد؛ صفحه‌ی وضعیت هم فقط با کلید `check` باز می‌شود و جزئیات حساس (نام کاربر دیتابیس) نشان نمی‌دهد.


## ۱۶) رفرال + کد هدیه + یادآور تلگرامی (پک v20 — گام ۲۰ رشد)

هر سه قابلیت با «قاعده‌ی سادگی»: کلید تنظیمات در پنل + منطق کوچک + مهاجرت خودکار. **هیچ کرون جدیدی اجباری نیست** — فقط یادآور یک کرون روزانه می‌خواهد.

### الف) دعوت دوستان (رفرال)
1. پنل ← تنظیمات ← گروه «دعوت دوستان — رفرال (v20)» ← **دعوت دوستان فعال** را روشن کنید
2. «پاداش هر طرف» = تعداد روز پرو برای هر دو طرف (پیش‌فرض ۷ روز)
3. در اپ، کارت «دعوت دوستان» در شیت **حساب کاربری** ظاهر می‌شود: کد یکتا + دکمه کپی + دکمه اشتراک در تلگرام + جای وارد کردن کد دوست

**قواعد:** هر حساب فقط یک‌بار می‌تواند کد کسی را فعال کند؛ کد خودتان قبول نمی‌شود؛ پاداش هر دو طرف «روی انتهای اعتبار فعلی» اضافه می‌شود و هرگز اشتراک فعلی را کوتاه نمی‌کند.

### ب) کد هدیه (تخفیف)
1. پنل ← تب جدید **«کدهای هدیه»** ← «کد جدید» — کد دستی یا خودکار، نوع: درصد یا مبلغ ثابت (ریال)، سقف استفاده (۰ = بی‌نهایت)، تاریخ انقضا (اختیاری)
2. کاربر در اپ، داخل شیت «انتخاب روش پرداخت» کد را وارد و «بررسی کد» می‌زند → تخفیف زنده دیده می‌شود
3. کد روی **هر دو روش پرداخت** کار می‌کند (درگاه و کارت‌به‌کارت)؛ شمارش استفاده فقط بعد از تأیید قطعی بالا می‌رود (پرداخت موفق درگاه / تأیید واریز در پنل)
4. سوئیچ کلی: پنل ← تنظیمات ← «کد هدیه (v20)» ← خاموش/روشن

**قواعد:** هر کاربر هر کد را فقط یک‌بار می‌تواند استفاده کند؛ مبلغ قابل پرداخت هرگز زیر ۱٬۰۰۰ ریال نمی‌رود؛ استفاده‌ها در ژورنال `coupon_redemptions` ثبت می‌شوند.

### ج) یادآور تلگرامی (یک کرون روزانه)
1. پنل ← تنظیمات ← گروه «یادآور تلگرامی (v20)» ← **روشن** کنید («بازه عقب‌افتادگی» پیش‌فرض ۳۰ روز)
2. DirectAdmin ← **Cron Jobs** ← Add New Cron Job — زمان: هر روز 08:00 (دقیقه = `0`، ساعت = `8`)
3. دستور:
   `/usr/local/bin/php /home/USERNAME/domains/app.hojre24shop.ir/public_html/api/cron/reminder-cron.php`
4. راستی‌آزمایی: `https://app.hojre24shop.ir/api/cron/reminder-cron.php?check=karam-reminder-check`

پیام فقط برای کاربرانی می‌رود که **با تلگرام وارد شده‌اند** (ربات حق شروع گفت‌وگو ندارد) و کارِ عقب‌افتاده دارند: «شما N کار عقب‌افتاده دارید» + ۳ عنوان اول. روزی حداکثر یک پیام (گارد فایل وضعیت)؛ اجرای دستی با `--force`.

### د) چرخه بازخورد
سند اجرایی: `docs/FEEDBACK.md` — سه سؤال، راه جمع‌آوری (کانال تلگرام پشتیبانی) و فرمت ثبت پاسخ‌ها. کدی نصب نمی‌خواهد.

### مهاجرت دیتابیس (خودکار و تکرارپذیر)
- رفرال: ستون‌های `users.referral_code` و `users.referred_by` + مقدار `'referral'` در ENUM اشتراک — بار اولی که کاربر شیت حساب را باز می‌کند
- کد هدیه: جدول `coupon_redemptions` + ستون‌های `coupon_id` و `discount_rials` روی واریزی‌ها — بار اولی که تب کدهای هدیه باز می‌شود
- ارتقای دستی اختیاری: `deploy/upgrade-v1.2.sql` (phpMyAdmin ← SQL) — لازم نیست ولی اضافه است

## ۱۷) کلید خاموش‌کردن پرداخت‌ها (پک v22 — گام ۲)

کلید «توقف اضطراری فروش»: با یک سوییچ در پنل، شروع همه‌ی پرداخت‌های جدید سمت سرور بسته می‌شود — بدون دست‌زدن به کد و بدون ری‌استارت. تصمیم همیشه **سمت سرور** است (`backend/src/Payments/PaymentsPolicy.php`)؛ اپ فقط نمایش می‌دهد.

### منطق تصمیم
`effective = کلید اصلی && سوییچ پلتفرم && حداقل یک روش فعال`

| کلید تنظیمات | نقش | پیش‌فرض |
|---|---|---|
| `payments_master_enabled` | کلید اصلی — خاموش = بسته‌شدن همه‌چیز | روشن |
| `payments_enabled_web` | فقط نسخه‌ی وب (PWA) | روشن |
| `payments_enabled_android` | فقط اپ اندروید (هدر `X-App-Platform`) | روشن |
| `payments_disabled_message` | پیام نمایشی به کاربر در اپ | خالی = پیام پیش‌فرض |
| `gift_codes_enabled` | **مستقل از کلید اصلی** — کدهای هدیه معتبر می‌مانند (نام قبلی: `gift_enabled` — با پک v1.5 خودکار تغییر نام می‌یابد و مقدار قبلی حفظ می‌شود) | روشن |

پلتفرم کاربر از هدر `X-App-Platform` خوانده می‌شود (نبودن = وب)؛ اپ این هدر را روی همه‌ی درخواست‌ها با `Capacitor.getPlatform()` می‌فرستد.

### استفاده
1. **بستن فروش:** پنل ← تنظیمات ← گروه اول «کلید اصلی پرداخت» ← سوییچ کلید اصلی ← دیالوگ تأیید ← «بله، ببند» ← **ذخیره** (ثبت در Audit)
2. **پیام اختصاصی:** همان گروه ← «پیام نمایشی» — مثلاً «در حال جابه‌جایی درگاه؛ تا ساعت ۱۸ برگردید»
3. **فروش فقط در اندروید (پیش از بازبینی بازار):** سوییچ «پرداخت در وب» خاموش، «پرداخت در اندروید» روشن
4. **وضعیت در یک نگاه:** داشبورد پنل — وقتی هر پلتفرمی بسته باشد بنر زرد بالای آمار می‌ماند

### چه چیزهایی بسته/باز می‌مانند؟
- **بسته:** شروع سفارش درگاه، ثبت درخواست کارت‌به‌کارت (هر دو ۴۰۳ با `code=payments_disabled`)، شماره کارت در اپ
- **باز (استثناها):** بازگشت/تأیید سفارش‌های قبلی از درگاه (callback)، وضعیت سفارش‌های موجود، اشتراک فعلی کاربران پرو، استعلام و مصرف کد هدیه، تأیید/رد واریز از پنل ادمین

### اپ چطور رفتار می‌کند؟
- UI پرداخت (پلن‌ها + دکمه خرید) کامل مخفی می‌شود؛ فقط کارت کهربایی «پیام + فیلد کد هدیه» می‌ماند
- وضعیت در IndexedDB کش می‌شود؛ **اندروید** اگر سرور در دسترس نباشد «بسته» فرض می‌کند (fail-closed) و **وب** «باز» (fail-open) — منبع حقیقت همیشه سرور است
- بیلد بدون پرداخت برای بازار: `cd mobile && bun run build:www:bazaar` (ثابت `VITE_PAYMENTS_BUILD=off`) — کل UI پرداخت از این بیلد حذف می‌شود. در بیلد ابری (GitHub Actions) هر دو APK خودکار ساخته می‌شوند: `karam-latest.apk` (پیش‌فرض — سایت/به‌روزرسانی) و `karam-bazaar.apk` (بازار — فقط این فایل در پنل بازار آپلود می‌شود؛ آرتیفکت `karam-bazaar-apk`)

### مهاجرت دیتابیس (اختیاری)
`deploy/upgrade-v1.4.sql` — فقط سید ۴ کلید جدید (تکرارپذیر). بدون اجرای آن هم همه‌چیز با پیش‌فرض «روشن» کار می‌کند؛ کلیدها بعد از نصب پک در پنل قابل ویرایش‌اند.

`deploy/upgrade-v1.5.sql` — تغییر نام کلید کد هدیه: `gift_enabled` ← `gift_codes_enabled` (تکرارپذیر؛ مقدار قبلی ادمین حفظ می‌شود؛ اگر هم اجرا نشود، کد در اولین استعلام کد هدیه خودش این تغییر نام را انجام می‌دهد).
